# WAMR3D decisions

Short current reference for contributors and AI tools. `AGENTS.md` defines repository rules; `STATUS.md` lists current gaps. Detailed historical rationale has been removed.

## Fixed choices

- Rust core (edition 2021); JavaScript is used where it is simpler or faster.
- Compatibility target: three.js, pinned to one exact `three` version in `package.json`.
- Math uses `f32`; matrices are column-major (`Matrix4` = 16 values, `Matrix3` = 9).
- Coordinates are right-handed, +Y up, camera looks down −Z; Euler defaults to `XYZ`.
- Scene entities use generational handles. A `World` owns its entities and resources.
- Parity fixtures come from direct imports of `three/src/`, never compiled `build/` files.
- Visual reference is three.js WebGPU. WebGPU NDC depth is 0..1; front faces are counter-clockwise.

## Engine and API

- Math stores `f32` and computes with `f64` where needed for parity. Target parity tolerance is `1e-6 * max(1, |expected|)`; non-finite values must match.
- SIMD is enabled for supported Wasm builds and must agree with scalar results.
- Scene graph, transforms, cameras and picking live in `engine/core`; built-in geometry and object types live in `engine/objects`.
- Generational handles cross the Wasm boundary as `bigint`. Low-level APIs are batched; `wamr3d/compat` provides three.js-style classes and chaining.
- The compatibility API stores transforms in JavaScript and synchronizes changes in batches. Do not mix low-level transform writes with compatibility getters on the same objects.
- Object-API math values are JavaScript (`compat/values.js`, and `Color` in `compat/math.js`): `Vector2/3/4`, `Quaternion`, `Euler`, `Matrix3`, `Matrix4`, `Box3`, `Sphere` and `Color` follow three.js's behaviour with 64-bit numbers. As engine objects every call crossed into WebAssembly and every `new Vector3` allocated engine memory and a finalizer, which made them 2.3× to 57× slower than three.js (2026-10-16, `bench/compat.mjs`); measured each in its own process, they now take the same time as three.js's. CSS colour parsing stays in the engine. `Plane`, `Ray`, `Frustum`, `Line3`, `Triangle`, `Spherical` and `Cylindrical` stay engine classes: JavaScript values passed to them are copied into temporary engine values (`toEngine`), and engine values they return are copied out (`adopt`). The Rust math crate keeps its parity tests and serves the engine and the low-level API (D1-D3 apply there).
- Reading engine values without allocating: `matrixWorldPtr`, `matrixPtr` and `worldValuePtr` return addresses inside the module that the object API reads through one cached `Float32Array` view. `object.matrixWorld` is read again only when an engine call through the object API has happened since the last read (`readStamp`); once the application takes the world with `getWorld()`, every read goes to the engine.
- Explicit low-level disposal frees resources. Destroying an entity does not dispose its geometry or material.
- Renderer split: Rust/Wasm prepares frame data and WGSL; JavaScript owns and issues WebGPU device, pipeline, buffer, texture and render-pass calls.
- Frame preparation keeps per-draw work small: a draw's entry holds its material's handle (materials are shared and carry a name, so copying one per draw meant an allocation), the draw order is a stable sort of 4-byte indices rather than of whole entries, and texture-set interning compares each draw with the previous one before hashing. Measured on 2026-10-16 at 50,000 separate meshes, this cut the CPU submit time from 67 ms to 44 ms (WebGPU) against the previous release.
- Data the engine does not hold is handled where it lives: instance matrices are passed to `World.raycastInstances` in one call (the low-level `raycast` skips instanced objects and sprites); sprites are picked in JavaScript against the quad facing `raycaster.camera`; a line loop's closing index is built by the host and kept per geometry until its index changes.
- Shadows: up to `MAX_SHADOWS` = 16 maps per frame in one depth texture array, allocated by the hosts with as many layers as frames have needed. A directional or spot light takes one layer, a point light six (90° square faces, +x, -x, +y, -y, +z, -z, of `mapSize.width`); the fragment shader picks the face by the largest component of the normal-biased direction from the light, and halves the point light's filter radius in face texels, matching three.js's offsets on the unit sphere. Lights whose maps no longer fit draw unshadowed. `BasicShadowMap` makes one comparison at the nearest texel's centre; every other type uses the five-tap PCF (three.js's WebGPU renderer also draws `PCFSoftShadowMap` as PCF; VSM is not implemented and warns).
- Frame format: a draw's material settings live in a per-material block of 256 floats (1 KiB), packed once per distinct material per frame and bound with a dynamic offset beside the per-object block (64-float stride, 32 read: model matrix, normal matrix, flags, first skin matrix + 1, sprite centre). Material blocks hold colours, factors, the physical layers' parameters, the environment's index and rotation, and a map table: per map, the first two rows of its uv transform with its texture slot + 1, and its uv set. Custom materials (effects, shader materials) put 16 settings in place of the sprite and environment rotation. Draw info has eight numbers: pipeline, texture set, start, count, instances, instance count, material block, custom shader.
- Textures per draw: 12 slots shared by 24 kinds of map. Maps take the first free slot in map-table order, and maps reading the same texture share one, so a glTF occlusion/roughness/metalness image takes one slot; the displacement map always takes slot 9, the one the vertex stage reads. Maps beyond the slots are left out. Each map is sampled through a `switch` on its slot, uniform across a draw. With the shadow array, the environment stack, the transmission copy and the VSM moments the fragment stage reads 16 textures, WebGPU's guaranteed limit, with 14 samplers.
- Extra vertex inputs (tangent, `uv1`, `skinIndex`, `skinWeight`) are interleaved by the host into one buffer (56 bytes per vertex), so a draw needs 7 of WebGPU's 8 vertex buffers; geometries without them bind a zero-stride buffer of zeros (pipeline-key bit 10).
- Skinning on the GPU: the engine keeps a `Skin` component (bones, inverse bind matrices, bind matrix, bind mode) and computes, per skinned object per frame, `bindMatrixInverse * boneWorld * boneInverse * bindMatrix` for every bone (the attached mode's inverse is that of the mesh's current world matrix). The matrices go to one float texture, 256 per row; the shader sums the four weighted matrices. Skinned meshes are not frustum-culled (bones move vertices beyond the geometry's bounds); raycasts pose a copy of the geometry on the CPU.
- Morph targets on the CPU: a geometry shared by meshes with different weights cannot be blended in place, so a morphed mesh draws its own engine geometry, blended (`morph.<attribute>.<i>` attributes of the base) only when weights or targets change. Picking and bounds see the blended shape. Morph-then-skin order is that of three.js.
- Transmission as three.js does it: opaque draws (and the background) go first into a mipmapped half-float copy as large as the target; transmissive draws read it along the refracted ray at a level from roughness and ior. Draw order is opaque, transmissive, blended. The copy is read trilinearly, not with three.js's bicubic filter.
- Area lights without LTC tables (three.js ships them as an add-on): the diffuse part uses the polygon's exact cosine form factor (the LTC evaluation with the identity), the specular part GGX towards the rectangle's point nearest the reflected view ray, its roughness widened by the light's equivalent radius over the distance. Highlights of large lights on smooth surfaces differ from three.js.
- VSM: depth maps are rendered as for PCF, then blurred into a half-float array of mean and deviation (vertical, then horizontal, `blurSamples` taps over `radius` texels) and tested with Chebyshev's bound, as three.js does.
- Several environment maps: every distinct environment of a frame (the scene's, materials' own `envMap`, up to eight) is prefiltered at one `lodMax` (the largest, lowered until the stack fits 8192 texels) and stacked in one texture; the material block holds the index and rotation.
- Points and lines above one pixel are drawn as instanced quads, six vertices per point or segment, with the geometry read per instance (indexed geometries are unrolled by the host). Point sizes follow three.js's WebGLRenderer (`size` times the pixel ratio, attenuated by half the viewport height over the distance); three.js's WebGPURenderer draws one-pixel points. `linewidth` widens `LineBasicMaterial` too, which three.js ignores; the `Line2` add-ons map onto it.
- Post-processing effects are engine shaders (WGSL and GLSL) selected by a material's `custom` id 1-6 and drawn on a 2 x 2 quad; the add-ons build three.js's EffectComposer API over them. A `ShaderMaterial` gets an id from 16 on; the WebGL 2 host compiles its GLSL with three.js's prefixes and built-in uniforms, renames its `main` to flip render targets like the engine's shaders, and uploads its own attributes (integer ones as integers). WebGPU draws such materials unlit.
- Audio and helpers that follow other objects update in `_onFrame`, which the renderer calls during its traversal: world matrices are computed in WebAssembly, so JavaScript `updateMatrixWorld` overrides would not run.
- Earcut 3.0.2 (ISC, Mapbox) is vendored in `compat/lib/earcut.js` with its notice; shapes and extrusions are triangulated in JavaScript.
- Wireframes (pipeline-key bit 9) draw a line list whose index the host builds per geometry and draw range, three edges per triangle as three.js does (shared edges twice), and caches until the geometry's index changes. Shadow passes still draw the filled mesh.
- Cube textures are turned on upload into an equirectangular texture four faces wide (same 8-bit format, capped at the device's largest texture size) by a small pass in each backend, sampling the cube along (-x, y, z) as three.js does; environment prefiltering and backgrounds then treat them as equirectangular images. This keeps one prefiltering path and one background shader per backend at the cost of one resampling.
- Source layout: files over about 1,000 lines are split by area. `compat.js` re-exports the object API from `compat/` (live bindings share the one `World`); the WebGPU host's prefiltering and background pass are in `webgpu/environment.js`; the wasm bindings split `World` across several `impl` blocks, which wasm-bindgen merges into one class.
- Attributes reach the engine as floats: `normalized` integer arrays are converted to 0..1 or -1..1 on upload, interleaved attributes are copied out one by one. The pipeline key carries the colour width (bit 8, three or four floats), the line-loop flag (bit 7) and the wireframe flag (bit 9).
- Polyhedra (tetrahedron, octahedron, dodecahedron, icosahedron and `PolyhedronGeometry`) are built unindexed as in three.js; the torus knot, lathe and capsule are indexed. All shapes are built in Rust from the constructor parameters.
- Engine code does not import three.js. CDN reference builds are limited to comparison/reference pages; committed fixtures let regular parity checks run without three.js installed.

## Compatibility limits

- The object API covers three.js's core classes and the common add-ons; `STATUS.md` and `MIGRATION.md` list what is missing (GLTFLoader, other format loaders, TSL).
- Two backends draw the same frames: WebGPU (`webgpu.js`, WGSL) and WebGL 2 (`webgl.js`, GLSL ES 3.00). The engine prepares frames independently of the API; both shader sets live in `engine/renderer_webgpu` (`shaders.rs`, `glsl.rs`), and the std140 uniform blocks keep the WGSL layout, so the same buffers upload to both. The object API's renderer picks with `backend: 'auto'` (WebGPU, then WebGL 2, then the browser's software WebGPU adapter), `'webgpu'` or `'webgl'`; `forceWebGL` and `WebGLRenderer` mean `'webgl'`. TSL/node rendering and three.js's own WebGL shader sources are not ported.
- WebGL 2 specifics: canvas frames are drawn into a linear `RGBA16F` target and encoded to sRGB by the output pass, so blending happens in linear light as on WebGPU (without `EXT_color_buffer_float` the shader encodes directly and blends in sRGB space, and tone mapping, float render targets and environment prefiltering are skipped with a warning); render targets are single-sampled and drawn with y flipped (`flip_y`, front face turned to clockwise) so their rows are stored top first as on WebGPU; clip depth is remapped from the engine's 0..1 to -1..1 in the vertex stages.
- Background textures follow three.js: equirectangular ones around the camera (from the prefiltered map when blurred, on a sphere of radius 3 × the view's half height for orthographic cameras), others stretched over the frame without their uv transform.
- The standard material follows three.js's lighting model, including its 16 × 16 split-sum table (read with the same bilinear filtering in WGSL) and its geometry roughness. Ambient and hemisphere light is diffuse only, so metals without an environment map are dark, as in three.js.
- Each map has its own uv transform and uv set (`texture.channel`). The normal map's tangent frame comes from the `tangent` attribute when the geometry has one, else from screen-space derivatives of the map's coordinates. `alphaMap` is read from the red channel: three.js's WebGPU path multiplies the opacity by the whole texel and keeps the first component, although its documentation says green; grey maps read the same.
- `MeshPhysicalMaterial` draws clearcoat (with `clearcoatNormalMap` or the surface's geometric normal), sheen (Charlie distribution, Neubelt visibility and the sheen albedo terms of three.js's physical lighting model; `sheenRoughness` is kept to 0.07..1 as three.js's WebGL renderer does, since 0 is undefined) the specular layer, iridescence, anisotropy and transmission with dispersion, and every layer's maps. `MeshToonMaterial` without `gradientMap` smooths its step from screen-space derivatives of the normal taken before any branch (WGSL needs uniform control flow), treating the light direction as constant across a pixel; three.js differentiates n·l directly. With a gradient map it reads red at (n·l / 2 + 1/2, 0) at level 0.
- Light maps add their texel times `lightMapIntensity` to the irradiance from all around (basic materials: the texel over π replaces full light), as three.js's node materials do; the ambient-occlusion map now also dims basic materials. Bump maps follow three.js's surface-gradient method and are ignored when a normal map is present. The specular map scales the Blinn-Phong highlight only (three.js also uses it for the environment of basic, Lambert and Phong materials, which WAMR3D does not draw). Displacement moves vertices in the main pass only.
- Rust math structs avoid hidden pointers and unsafe code. Typed-array views into Wasm memory become invalid after memory growth; refresh them before reuse.
- Known behavioral deviations and unsupported properties are documented in `MIGRATION.md` and `STATUS.md`.

## Cited decision IDs

Code comments and `AGENTS.md` cite these IDs; keep them stable.

- **D1** Each function widens `f32` inputs to `f64`, computes as three.js does, and rounds once on store. Chained calls round at each step.
- **D2** Parity tolerance `|got − expected| <= 1e-6 * max(1, |expected|)`; non-finite values match exactly.
- **D3** The SIMD path uses `f64x2` in scalar operation order, so it is bit-identical to scalar.
- **D4** Rust API: three.js names in `snake_case`; `target` out-parameters become return values; `null` becomes `Option`; overloads are split; string enums become Rust enums; out-of-range indices panic.
- **D16** `engine/core/src/constants.rs` holds the buffer usage and attribute type values from three.js `constants.js`.
- **D18** Integer typed-array stores wrap as JavaScript does (`Uint8ClampedArray` clamps and rounds half to even); they do not saturate.
- **D21** `engine/bindings` (package `wamr3d`) is a thin `wasm-bindgen` shell with no `unsafe`; zero-copy views are built in JavaScript.
- **D27** Visual parity compares against stored three.js WebGPU renders, within the tolerance in `parity/visual/cases.js`.
- **D32** Renderer split; see "Engine and API".
- **D39** Random helpers use a SplitMix64 generator, seeded by `init()` and resettable with `setRandomSeed`; `seededRandom` stays Mulberry32.
- **Section 5 / 5.3** Core model and ownership: a `World` owns everything; `destroy` leaves children alive as roots and `destroy_recursive` destroys the subtree; geometries, materials, render targets and interleaved buffers are freed only by `dispose_*`; reference counts are informational; arena slots are reused.
- **Section 6** Language split; see "Fixed choices" and "Engine and API".
